# 範本：DBR 迭代紀錄（`type: iteration`）與版本紀錄（`type: version`）

一輪設計本位研究（DBR）迭代一檔。`version` 只填「本輪變更」與「證據」兩段，其餘段落可省略。日期、版本號、決議不確定時填 `AUTHOR_INPUT_NEEDED`，不猜測。

```markdown
---
log_id: {專案代碼}-IT-YYMMDD-001
date: YYYY-MM-DD
type: iteration
project: {專案名稱}
version: V{n}
participants: [{研究者}, {共同決策者}]
tags: [DBR, {理論框架}, {技術要素}]
status: open
next_actions:
  - {下一輪要做的事}（負責：{人}，期限：YYYY-MM-DD）
related: []
attachments: []
---

# 本輪目標

一句話說明這一輪要解決的設計問題，以及對應的研究問題編號。

# 設計原則

| 編號 | 設計原則 | 理論依據 | 本輪是否調整 |
|---|---|---|---|
| DP1 | | | 維持／新增／修改 |

# 本輪變更（V{n-1} → V{n}）

| 面向 | V{n-1} | V{n} | 變更理由 |
|---|---|---|---|
| 提示詞 | | | |
| 檢索資料庫 | | | |
| 介面 | | | |
| 案例 | | | |

# 證據

列出支持本輪變更的資料來源，量性與質性分開；數字標明來源與是否經統計確認。

- 量性：{SUS、正確率、token 成本、系統日誌}（來源：{檔名}；統計確認：是／否）
- 質性：{放聲思考、訪談、觀察}摘要（逐字稿：{相對路徑}）

# 問題與未解

- 本輪仍未解決的問題與原因。

# 下一輪

- 下一輪的假設、要驗證的設計原則、預計測試場次與受試者數。

# 附件

- `圖片/xxx.png`：說明
```

## 填寫提醒

- 設計原則編號跨輪固定，被淘汰的原則保留並標「已淘汰（V{n}）」。
- 「證據」段只放本輪實際收到的資料；前後測比較與顯著性交 `bob-statistics`。
- 版本號與程式碼倉庫的 tag 或 commit 對應時，在 `attachments` 或正文記錄 commit 短碼。
